# CONTENT INTELLIGENCE MONITORING
## Watch everything that can change the truth — score every signal — act on the few that matter

---

## What This Skill Is

A published page is a snapshot of facts that keep moving. A regulation changes, an airline rewrites
its cargo policy, a competitor fills the gap you were about to take, a community thread surfaces a
fear no one has answered — and the page that was correct last month is now quietly wrong. In a
maximum-risk niche, *quietly wrong* is the worst state there is: wrong information means a pet
denied entry. Content Intelligence Monitoring is the system that watches all of it at once and tells
you, every week, the small number of things to fix **first**.

It does two things. First, it runs a **12-stream monitor** across everything that moves the
business — regulatory portals, destination authorities, airline policies, competitor content and
pricing, search performance, AI citations, community fear signals, reviews, and broad market
chatter. Second — and this is what makes it a system and not a dashboard — every detected signal is
fed into a **RICE decision engine** that scores it `(Reach × Impact × Confidence) ÷ Effort` and
routes it to a service level: **TODAY**, **48 hours**, **this week**, or the **monthly cycle**. The
loudest signal doesn't win; the highest-consequence one does. *(Library: M-27 RICE; F-05
Dashboard-to-Action; F-12 Content Update Priority Matrix.)*

## The Two Components

1. **The 12-stream monitor** — what is watched, how often, and how. Four regulatory streams (the
   ones where being wrong = real harm), three competitor streams, two search/AI streams, three
   community/market streams. Each stream has a cadence and a method; the live collectors are real in
   shape and honestly gated on API keys. *(Library: F-10 Monthly Content Intelligence Cycle; F-39
   Position-Drop Alerting; P-48 weekly AI-citation tracking.)*
2. **The RICE decision engine** — the scoring rule every signal passes through. `rice_score()` turns
   a signal into one comparable number; `route()` files it in the action queue by consequence, not
   volume. This is the part that converts "we monitor a lot" into "we know what to do today."
   *(Library: M-27; F-05; F-12.)*

## Functional Quality Threshold (Check 46)

This skill's real output is **proven** only when the engine **deterministically produces** a weekly
intelligence report meeting all four gates:

1. **Every signal is RICE-scored and routed by the engine** — `(R × I × C) ÷ E` computed in code and
   filed into a band (TODAY / 48HR / THIS WEEK / MONTHLY) by `route()`, never assigned by hand.
2. **Every signal traces to a verified source already in this repository** — a Source-Bank C-ID, the
   competitor content-gap matrix, a real community quote, or the master customer profile. **Zero
   fabricated signals.** *(P-07 Independent Verification; P-02 Wrong Information Causes Real Harm.)*
3. **All 12 streams are represented with an honest connection status** — a live collector with no API
   key set is listed as *awaiting connection* and contributes **no** signal; the engine never
   invents live data. *(P-07.)*
4. **Re-running the engine reproduces the report exactly** — the report date is fixed (not
   `Date.now()`), so the output is byte-identical on every run. Determinism is what makes the output
   auditable.

Measured in `data/weekly-intelligence-report.md`: **7/7** signals scored & routed by the engine,
**7/7** traceable to a named in-repo source, **12/12** streams with honest status, and the report
reproduces byte-for-byte on re-run. A report with a hand-assigned band, a sourceless signal, or
fabricated live data is not done.

**Live-stream connection is NOT YET CONFIRMED** — the live collectors (GSC, Reddit, Perplexity, GA4,
Visualping) are real in shape but gated on keys; with no keys this cycle, **0/10** live streams are
connected and the report is built entirely from the verified in-repo signals. Connecting the streams
(set the env keys + Visualping webhook) and confirming detected changes flow through the same RICE
engine is the post-connection validation step — the monitoring analogue of the independence test
(Check 47). It does not block the deterministic threshold above.

## Environment Variables

```
PROJECT_ROOT=             # absolute path to the project root on this machine
MONITOR_REPORT_DATE=      # optional — fixes the report's cycle date (default 2026-06-01) for reproducibility

# Optional — only to CONNECT the live collectors. The deterministic core (RICE scoring +
# routing + report generation) needs NO keys and runs anywhere. A stream with no key is
# listed "awaiting connection" and contributes no signal — it is never fabricated.
VISUALPING_WEBHOOK_URL=   # streams 1-3, 5 — page-change webhooks (MOCCAE, destinations, airlines, competitors)
SERPAPI_KEY=              # stream 5 — competitor SERP/content changes
ANTHROPIC_API_KEY=        # stream 6 — monthly Trust Score re-audit
REDDIT_CLIENT_ID=         # streams 7, 10 — competitor positioning + community fear signals (PRAW)
GSC_REFRESH_TOKEN=        # stream 8 — Search Console daily performance
PERPLEXITY_API_KEY=       # stream 9 — AI citation tracking
GBP_API_KEY=              # stream 11 — Google Business Profile review monitoring
```

Automation 5/5 (the highest ceiling in the program): the monitor collects and the engine scores,
routes and writes the report end to end. What stays human is **calibrating the RICE inputs** (how
bad is the worst case? how sure are we?) and **reading the queue** to act. See
`files/04-automation-spec.md`.

## Standalone Test

Someone in any market can use this skill alone: list the streams that move *their* truth (the
regulator, the competitors, the search panel, the community), set a cadence and a collector for
each, score every detected signal with `(R × I × C) ÷ E`, and let `route()` file it into a TODAY /
48HR / week / month queue. The method — watch broadly, score by consequence, act on the few that
matter — is fully portable; only the streams and the verified sources are niche-specific.
